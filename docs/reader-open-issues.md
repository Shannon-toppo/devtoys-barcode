# 読み取り処理の課題（引き継ぎ）

2026年10月14日時点、`main`のコミット`95fdfc1`で残っていた3つの課題を、2026年10月15日に調べました。結果は次のとおりです。

| 課題 | 結果 |
|---|---|
| 1. 同じ画像の結果が実行ごとに変わる | 解決。読み取り処理ではなく、計測ツールが作るノイズ画像が実行ごとに変わっていた |
| 2. PDF417の座標が一部しか返らない | 解決。欠けた側の端を、ZXingの白黒画像から探して補う |
| 3. 回転したPDF417が2つあると2つ目を取りこぼす | 対応不要。最終結果で欠ける配置は48通り中0通り |

課題ごとに、もとの記録（わかっていた事実と推測）を残し、そのあとに調査の結果を書いています。

## 前提

### 対象のコード

読み取り処理は`src/DevToys.Barcode/Helpers/`にあります。

| ファイル | 役割 |
|---|---|
| `BarcodeHelper.Read.cs` | 読み取り全体の流れ。本処理、領域ごとの読み取り、再試行、1次元の確認、結果の整列 |
| `MultipleBarcodeDecoder.cs` | ZXingの複数検出（`GenericMultipleBarcodeReader`）を並列で再実装したもの。PDF417の座標補正もここ |
| `BarcodeRegionFinder.cs` | 暗い画素のかたまりを領域として切り出す |
| `BarcodeImageEnhancer.cs` | 照明とコントラストの正規化 |
| `BarcodeImageRotator.cs` | 傾き再試行用の回転 |

処理の流れは次のとおりです。

1. 1次元、QR/Data Matrix/Aztec、PDF417の3系統に分け、フル解像度の画像を0度と90度で並列に読む。PDF417はフル解像度では正立だけ。
2. 読み取り済みの範囲を白く塗りつぶし、残った暗い領域を1つずつ切り出して読む（`FindInRegions`）。
3. 手順1と2で何も見つからなかったときだけ、長辺1600ピクセルに縮小した画像で再試行する。順に、白黒反転、短いITF、正規化、傾き6方向、拡大。
4. 1次元の結果は、再デコードとバーの高さで確認してから採用する。
5. 形式と文字列が同じ結果を1件にまとめ、上から下、左から右の順に並べる。

### 計測の方法

計測ツールは`tools/DevToys.Barcode.Measure`にあります。ソリューションには入っていません。

```
dotnet run -c Release --project tools/DevToys.Barcode.Measure -- <コマンド>
```

| コマンド | 内容 | 現在の値 |
|---|---|---|
| `matrix` | 13形式に9種類の劣化をかけた読み取り率 | 676試行中605、364条件中329が全試行合格 |
| `fp 2` | バーコードのない画像での誤検出 | 252枚中0枚（課題1の修正で画像の組が変わった。修正前の値は252枚中1枚） |
| `perf test-images 5` | 大きな画像の速度とキャンセルの遅れ | 下の表 |
| `corpus <出力ファイル> test-images` | 約1053枚の全結果を座標つきで1行ずつ書き出す | 2つの版を`diff`で比べるのに使う |
| `pdf417 [bounds\|background\|pairs]` | 課題2と課題3の再現。座標がシンボルを覆う割合と、2つのPDF417の48通りの配置 | 下の各課題を参照 |
| `small`、`breakdown` | 小さな画像の速度、段階ごとの内訳 | |

速度の現在値（10コアのMac、リリースビルド、中央値）は次のとおりです。

| 画像 | 所要時間 |
|---|---|
| 6000×4500、バーコードなし | 約580ミリ秒 |
| 4000×3000、写真風の模様、バーコードなし | 約460ミリ秒 |
| 4000×3000、小さなEAN-13が1つ | 約125ミリ秒 |
| 4000×3000、小さなData Matrixが1つ | 約90ミリ秒 |

速度は実行のたびに揺れます。変更前と変更後を交互に複数回測り、中央値で比べてください。順序を入れ替えた計測も必要です。あとから測った側が15〜25%遅く見えたことがあり、原因は温度による性能低下でした。

## 課題1: 同じ画像の結果が実行ごとに変わることがある

### わかっている事実

- `corpus`を同じコードで繰り返し実行すると、ランダムノイズの画像（`fp noise N`の行）1枚で、あるときだけ誤検出が出ることがあります。
- 観測した例は次の2件です。
  - `main`の`7a98210`で2回実行し、2回目だけ`fp noise 23`に`RSS_EXPANDED:(01)138821796993941@365,438,388,90`が出た。
  - 高速化のPR（`956eaeb`）で3回実行し、1回目だけ`fp noise 11`に`RSS_14:139200833197402@548,329,138,166`が出た。
- 対象の画像は毎回違い、出る形式はRSS-14かRSS Expandedでした。
- 高速化の前後どちらでも起きているので、高速化が原因ではありません。
- ノイズ以外の画像（約1000枚）の結果は、どの実行でも一致していました。
- その後、`95fdfc1`の前後で各3回、計6回実行したときは一度も起きませんでした。

### わかっていないこと

- 原因。再現条件も特定できていません。
- 起きた5回の実行は、速度、テスト、`matrix`、`fp`の計測を続けて流した直後でした。起きなかった6回は別の時間帯です。マシンの負荷や温度が関係している可能性がありますが、確かめていません。

### 調べる価値がありそうな箇所（推測）

- 並列に動く作業の間で共有している状態。系統ごとの並列、`MultipleBarcodeDecoder`の部分画像の並列、反転の同時実行があります。
- 並列の作業の完了順によって、後段の入力が変わる箇所。読み取り済みの範囲の塗りつぶしや、重複の除去が候補です。
- 1次元の確認（`IsGenuineOneDimensional`）。RSS系の誤検出はここを通過しているはずです。
- ZXingのRSSリーダーは、行をまたいで候補を蓄積する内部状態を持ちます。リーダーのインスタンスを使い回していないかを確認してください。

### 進め方の案

1. まず再現率を上げる。ノイズ画像だけを数百回読み、結果が割れる画像を集める。並列度を変える（`DOTNET_PROCESSOR_COUNT`）、ほかの負荷をかけながら実行する、といった条件も試す。
2. 結果が割れる画像が1枚でも固定できたら、並列を1つずつ外して、どの並列が原因かを絞る。
3. 原因が特定できたら直し、同じ画像を多数回読んで結果が一致することを確かめるテストを足す。

### 影響

ノイズ画像での誤検出がまれに増える程度です。通常のバーコード画像で結果が変わった例は観測していません。ただし、原因が共有状態の競合なら、ほかの形で現れる可能性があります。3つの中では、これを最初に調べることを勧めます。

### 調査の結果（解決）

原因は計測ツールでした。読み取り処理には問題がありませんでした。

- 結果が割れた`fp noise 11`と`fp noise 23`は、どちらも`seed % 4 == 3`の画像です。この種類のノイズは、3ピクセル四方のブロックごとに`new Random(HashCode.Combine(seed, x, y))`で白か黒を決めていました。.NETの`HashCode`はプロセスごとに乱数で初期化されるので、同じシードでも実行のたびに別の画像ができていました。ほかの種類のノイズは`new Random(seed)`だけで作るので、毎回同じ画像です。
- `tools/DevToys.Barcode.Measure/FalsePositives.cs`で、ブロックの値をプロセスによらないハッシュ（`BlockHash`）で決めるようにしました。修正後は`corpus`を続けて2回実行し、全行が一致しました（修正前のコードと修正後のコードの両方で確認）。
- `fp`コマンドには別の不具合もありました。ラムダ式がループ変数`i`をそのまま捕捉していたため、実行時の`i`はループ終了後の値（24）になり、`binary-*`の画像はすべて`kind: 0`で作られていました。`seed % 4`を使うように直したので、`fp 2`の画像の組が変わっています。新しい組では、修正前と修正後のどちらの読み取り処理でも誤検出は0枚です。
- 読み取り処理が同じ画像に毎回同じ結果を返すことは、テスト`SamePicture_ReadManyTimesAtOnce_GivesTheSameResultsEveryTime`で確かめます。1次元、Data Matrix、90度回したPDF417、ブロックノイズを置いた画像を、8回同時に読んで結果を比べます。

## 課題2: PDF417の座標が一部しか返らないことがある

### わかっている事実

- ZXingが、PDF417の開始パターンか終了パターンの座標しか返さないことがあります。幅480ピクセルのシンボルに対して、報告される範囲は約70ピクセル分になります。
- 起きる条件として確認できたものは次のとおりです。
  - 25文字の文字列`Beta PDF417 second symbol`を90度か270度に回した画像。背景が白一色でも起きる。
  - `matrix`の`PDF417 / background 2`の3試行。実際の範囲が`1339,1015,480,112`のところ、`1748,1017,72,111`が返る。
  - そのほか、回転した画像の一部。
- 返ってくる座標の位置そのものは正しく、シンボルの上にあります。`95fdfc1`より前は、位置も誤っていました。

### 影響

- 文字列の読み取りには影響しません。
- 並び順への影響は小さいです。位置がシンボルの端に寄るだけです。
- 読み取り済みの範囲の塗りつぶしが足りなくなります。残ったシンボルの大部分が次の領域ごとの読み取りに回り、時間を使います。同じ文字列なので、結果が重複することはありません。

### 調べること

- ZXingのPDF417の結果は8点（開始側4点、終了側4点）で、欠けた点は`null`になります。片側しかないときに、もう片側を推定できるかを調べてください。行数と列数、モジュール幅はZXingの検出結果から得られる可能性があります。
- 推定が難しければ、返ってきた範囲から外側へ暗い画素をたどって広げる方法もあります。1次元のバーの高さを画素から測る処理が`BarcodeHelper.Read.cs`にあり、参考になります。

### 調査の結果（解決）

ZXingが片側しか返さないのは、主に縮小した画像での再試行（正規化、ノイズ除去など）で読めたときでした。白一色の背景では、`pdf417 bounds`の540通り（5種類の文字列、4方向、27の配置）で一度も起きませんでした。`matrix`の`PDF417 / background 2`と`3`では、6試行すべてで起きていました。

8点の並びは次のとおりです。片側が見つからないと、その4点が`null`になります。

| 添字 | 点 |
|---|---|
| 0、1 | 開始パターンの外側の端（上の行、下の行） |
| 4、5 | 開始パターンの内側の端（上の行、下の行） |
| 2、3 | 終了パターンの外側の端（上の行、下の行） |
| 6、7 | 終了パターンの内側の端（上の行、下の行） |

欠けた側は`Pdf417EndFinder`で探します。`MultipleBarcodeDecoder`が、座標を元の画像の向きに戻した直後に呼びます。暗い画素をたどる方法は、背景が込み入っていると背景まで範囲に含めてしまうので、PDF417の構造を使いました。

- 各行は、開始パターン（17モジュール、最初のバーは8モジュール）、17モジュールの符号語の列、終了パターン（18モジュール、最初のバーは7モジュール）の順に並びます。
- 符号語はバーで始まり、スペースで終わります。符号語のバーの幅は最大6モジュールです。
- そのため、見つかったパターンの内側の端から17モジュールごとに、シンボルの高さ全体で白から黒に変わる境目があります。7モジュール以上の幅のバーで始まる境目が、反対側のパターンです。
- 境目は予想位置の前後2モジュールの範囲で探し、見つけるたびにモジュール幅を測り直します。測り直さないと、モジュール幅のわずかなずれが列の数だけ積み重なります。
- 判定には、シンボルを読んだときのZXingの白黒画像を使います。反転した画像から読めたときは反転した画像です。
- 境目が見つからないとき（シンボルが傷んでいる、反対側がない）は、点を補いません。

符号語の境目の判定で、6モジュールのバーを反対側のパターンと取り違える例が、縮小した画像で出ました。縮小でぼけると、6モジュールのバーと続くスペースの大部分が黒になるためです。実測では、パターンは7モジュールの範囲の96〜100%が黒、符号語は76%以下でした。判定のしきい値を90%にしています。

結果は次のとおりです。

- `corpus`で変わったのは、`PDF417 / background 2`と`3`の6行だけです。たとえば、実際の範囲が`1339,1015,480,112`のところ、`1748,1017,72,111`が`1338,1017,482,111`になりました。
- `pdf417 background`（`background 2`と`3`、各30シード）では、読めた58枚のうち55枚で、座標がシンボルの90%以上を覆い、はみ出しは10%以下です。残る3枚は幅は正しく、高さが84〜96ピクセルと短くなります。ZXingがパターンを一部の行でしか見つけていないためで、端の補完とは別の問題です。
- 端を探すのは、片側しかない結果が出たときだけです。`perf test-images 5`を修正前のビルドと交互に3回ずつ実行し、中央値に差はありませんでした。`matrix`（676試行中605）、`fp 2`（252枚中0枚）も変わりません。
- テスト`Pdf417EndFinderTests`で、3種類の文字列、4方向、どちらの側が欠けた場合も、ZXingが両側を見つけたときの点と1モジュール以内で一致することを確かめます。反対側がない場合に点を作らないことも確かめます。

## 課題3: 回転したPDF417が2つあると、2つ目を複数検出で取りこぼす配置がある

### わかっている事実

- PDF417を2つ置き、回転と位置を変えた48通りのうち10通りで、`MultipleBarcodeDecoder`の段階では2つ目が見つかりませんでした。`95fdfc1`より前は22通りでした。
- そのあとの領域ごとの読み取りで拾える場合があります。最終的な読み取り結果として何通りが欠けるかは、数えていません。
- このときの計測用プログラムは一時フォルダにあり、残っていません。再現には作り直しが必要です。

### 調べること

- まず、最終結果（`BarcodeHelper.Read`の戻り値）で2つ目が欠ける配置が何通りあるかを数えてください。0なら、対応は不要です。
- 欠ける配置があれば、どの段階で落ちているかを調べてください。ZXingの複数検出は、見つけたシンボルの左、上、右、下の4つの範囲を再帰的に探します。2つ目がどの範囲にも収まらない配置は、この方式では見つかりません。課題2で座標が一部しか返らないと、範囲の切り方も変わります。課題2を先に直すと、ここの件数も変わる可能性があります。

### 調査の結果（対応不要）

計測用の処理を`pdf417 pairs`として作り直しました。2つのPDF417（25文字前後の文字列）それぞれの向き4通りと、2つ目の位置3通り（右、下、右下）で48通りです。

- 最終結果で2つ目が欠ける配置は、課題2の修正の前も後も0通りでした。
- `MultipleBarcodeDecoder`だけで2つ目が見つからない配置は2通りです（2つとも正立で縦に並ぶ配置と、2つとも270度で横に並ぶ配置）。どちらも、そのあとの領域ごとの読み取りで見つかります。

最終結果に欠けがないので、手を入れていません。

## 範囲外で気づいている点

対応は不要ですが、調査中に関係してくる可能性があります。

- QRの座標は、3つの位置検出パターンの中心から求めています。各辺で約3.5モジュール分、実際より内側になります。
- Data Matrixの座標は、実際より約5ピクセル内側になります。
- 破損した1次元バーコードの座標が、隣のシンボルにかかることがあります。その場合、塗りつぶしで隣のシンボルを消してしまいます。
- テスト用の`TestImages.Compose`は、不透明な白の余白ごと画像を重ねます。配置によっては、先に置いたバーコードを上書きします。テスト用の画像を作るときは注意してください。
- RSS-14、RSS Expanded、MaxiCodeは、画像を生成する手段がありません。これらの読み取りは、実画像では一度も確かめていません。
- 実写の写真は、利用者が数枚を手動で試しただけです。計測はすべて合成画像です。
